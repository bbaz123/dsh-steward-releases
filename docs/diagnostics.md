# 诊断能力说明（v1.3.0）

这份文档说明 DSH 管家从 1.2.1 起新增的诊断能力、以及 1.3.0 增加的
**数据安全（备份 / 恢复 / 会话定点修复）** 能力：**它怎么找问题、凭什么下结论、什么情况下才会动文件。**

---

## 一、一句话定位

1.1.0 的管家是「体检器 + 更新器」；1.2.1 多了一条**诊断链路**；1.3.0 再并上一条**数据安全链路**
（备份中心 + 会话定点修复）：

```text
接管或受管启动 DSH
  → 采集真实现场（stdout / stderr / 端口 / 进程树 / 健康探针）
  → 提取证据
  → 命中诊断规则（19 条，含只用本机文件的离线环境层规则）
  → 有可逆修复计划的，才允许动手
  → 动手前备份 / 留档、动手后复验、失败自动回滚
```

**故障** 与 **更新** 从这一版起彻底分开：

- 故障 = DSH 现在跑不起来 / 跑得不正常 → 在【故障中心】处理；
- 更新 = 有新版可用、仓库有新提交、配套服务没启动 → 在【维护中心】，只在你手动点击时执行。

---

## 二、怎么用

### 图形界面（日常）

顶部工具栏从左到右：

| 按钮 | 作用 |
| --- | --- |
| 启动 / 诊断 DSH | 已经跑着就接管（绝不重复启动第二个），没跑就受管启动并采集现场，然后出诊断结论 |
| 一键修复 | 先诊断，再只修「有证据且能自动改回来」的故障；没有可自动修的故障时只给建议，绝不自动升级 |
| 重新体检 | 跑一遍本机环境体检（Node / npm / dsh / 插件 / 仓库 / 配套项目） |
| 打开 DSH 网页 | 已运行就直接开浏览器；没运行会问你要不要启动 |
| 配置文件 | 打开 `DSH管家.config.json` |
| 故障中心 / 维护中心 / 备份中心 / 运行日志 | 切换页面 |

【备份中心】（v1.3.0，独立窗口）15 个按钮：新建全量备份、分类备份、校验选中 / 校验全部、
预演恢复、执行恢复、打开备份目录 / vault、会话体检、定点修复会话、放行原生模块、版本信息、打开配置。

【故障中心】每条故障一张卡片，写明：

```text
等级 P0~P4 · 自动化 A0~A3 · 规则号
问题是什么 / 影响是什么 / 证据是什么 / 涉及哪个文件 / 风险多大 / 建议怎么做
```

【维护中心】保留 1.1.0 的全部批量能力（全套维护 = 原来的「一键修复」、检查更新、立即更新、
启动配套服务、可见窗口启动）以及逐项体检卡片。

### 命令行（自动化 / 排障）

```text
DSH管家.exe --diagnose        启动或接管 DSH，采集现场并输出诊断（只读，不改任何文件）
DSH管家.exe --repair --yes    先诊断，再对可自动修复的故障做最小可逆修复
DSH管家.exe --repair          预演模式：只显示要修什么，不写任何文件
DSH管家.exe --health          体检并写出 DSH管家-health.json（21 项）
DSH管家.exe --selftest        离线自测（沙箱 + 假 DSH，77 项，不碰真实环境）
DSH管家.exe --versions        版本信息（管家 / 系统 / Node / npm / dsh / 插件 / 备份 / 会话 / 网络）
DSH管家.exe --backup [--types sessions,settings,credentials,profiles,skills,storage,attachments]
DSH管家.exe --backups         列出全部备份（含升级前 / 恢复前快照与校验状态）
DSH管家.exe --verify <名|all> 校验归档完整性与 SHA256
DSH管家.exe --restore <名|latest> --dry-run [--types ...]    恢复预演，零改动
DSH管家.exe --restore <名|latest> --yes [--types ...]        执行恢复，先拍快照再挪旁
DSH管家.exe --sessions [--repair [--archive 名]]             会话体检 / 定点修复
DSH管家.exe --compat <插件名>@<版本>[,..]                    兼容性预检
DSH管家.exe --stop-dsh        只停「管家自己启动的」DSH 进程树
DSH管家.exe --help            帮助
```

退出码：`0` = 没有 P0/P1 故障（或命令成功）；`1` = 存在 P0/P1；`2` = 执行异常；`3` = 预演（未执行修复）。
兼容性预检单独一套：`0` 通过 / `1` 不兼容 / `3` 未知（**未知不当通过**）。

## 三、诊断数据在哪

全部在 exe 同级的 `diagnostics-data\` 下，默认只保留最近 30 份现场：

```text
diagnostics-data\
  captures\<会话ID>\
    stdout.log      启动脚本/进程的标准输出
    stderr.log      标准错误（DSH 的报错通常在这里）
    combined.log    合并后的完整现场（诊断的主要证据来源）
    launch.json     启动方式、命令行、进程号、退出码、健康地址
    process.json    进程号 / 子进程号 / 退出码 / 存活状态
    probe.json      健康探针结果
  diagnostics\<会话ID>\
    session.json      会话摘要
    environment.json  环境快照（Node / npm / dsh / DSH_HOME / profile）
    packages.json     依赖与插件版本
    findings.json     诊断结论（含证据与涉及文件）
    candidates.json   候选文件定位过程与命中结果
  recovery\<会话ID>\  恢复点：manifest.json + backup\（修复前原文件）
  selftest-report.txt 最近一次自测报告
```

有了这些，反馈问题时不需要再靠猜：现场、证据、结论、改了什么、怎么回滚，全都留档。

## 四、19 条诊断规则

| 规则号 | 等级 | 自动化 | 能不能自动修 |
| --- | --- | --- | --- |
| `DSH-JSON-BOM-001` JSON 清单含 BOM | P0 | A0 | **能**（自动修复第一条） |
| `DSH-JSON-BROKEN-002` 普通 JSON 损坏 | P0 | A3 | 不能，只诊断（不乱生成 JSON） |
| `DSH-MODULE-NOT-FOUND-003` 缺模块 | P0 | A2 | 不能，只诊断 |
| `DSH-PLUGIN-MISMATCH-010` 插件与主程序不匹配 | P1 | A2 | 不能，只诊断 |
| `DSH-DEP-DRIFT-020` 核心子包版本漂移 | P2 | A3 | 不能，只诊断 |
| `DSH-SESSION-CORRUPT-030` 会话日志损坏 | P0 | A1 | 第一版只诊断 |
| `DSH-NODE-INCOMPAT-040` Node 版本不兼容 | P0 | A2 | 不能（升级属于维护） |
| `DSH-NPX-CACHE-050` npx 缓存/内存问题 | P1 | A0 | 第一版只诊断 |
| `DSH-PORT-BLOCKED-060` 端口被占用 | P1 / P2 | A0 | 不能，只诊断 |
| `DSH-LAUNCH-BACKGROUND-070` 后台启动被误判 | P1 | A1 | 不能，只诊断 |
| `DSH-ENOENT-SUBPROC-080` 子进程日志缺失 | P0 | A2 | 不能（上游 bug） |
| `DSH-BACKUP-MISSING-090` 一个备份都没有 | P2 | A3 | 不能 → 去【备份中心】建第一份 |
| `DSH-BACKUP-STALE-091` 最近的备份过期 | P2 | A3 | 不能 → 去【备份中心】补一份 |
| `DSH-BACKUP-CORRUPT-092` 备份缺校验 / 边车损坏 | P1 | A3 | 不能（诊断不改文件） |
| `DSH-PLUGIN-COMPAT-100` 插件要求的宿主版本不符 | P1 / P2 | A3 | 不能（安装 / 升级前会拦） |
| `DSH-NODE-ENGINE-101` 插件要求的 Node 不符 | P1 | A3 | 不能（换 Node 影响面大） |
| `DSH-PLUGIN-DEPS-110` 插件依赖三层都解析不到 | P2 | A3 | 不能（改 profile 需你确认） |
| `DSH-NPMRC-ALLOWLIST-120` 原生模块白名单没覆盖 | P2 | A3 | 不能 →【备份中心】一键放行 |
| `DSH-SESSION-BATCH-031` 会话日志批量损坏 | P1 | A1 | **能**（从已验证归档定点修复，自动修复第二条） |

> 端口规则说明：**管家自己启动的 DSH 正在监听，不算故障**（这是正面证据）。
> 只有「别的进程占了你习惯用的端口」才会提示；当 DSH 本身健康、只是换了端口时，等级降为 P2 参考信息。

> 规则 12~19（090 / 091 / 092 / 100 / 101 / 110 / 120 / 031）是 v1.3.0 新增的**环境层规则**：
> 只用本机已有文件判定（备份目录 / `package.json` / `.npmrc` / 会话目录），**不走网络**，
> 所以离线跑 `--diagnose` 也能得到可复现的数据与插件健康结论。
> `DSH-PLUGIN-COMPAT-100` 与 `--compat` 用同一套判定：`peerDependencies` 数值窗口 + `engines.node`，
> 三种结论 OK / FAIL / **未知**，**未知绝不当通过**。

## 五、自动修复闭环（一）剥离 JSON 清单的 BOM

`DSH-JSON-BOM-001` 是两条可自动修复规则中的第一条，流程固定为：

```text
1. 前置校验   文件必须存在、必须仍有 BOM、SHA256 必须与诊断时一致
              （不一致 → 拒绝修复，并提示重新诊断）
2. Recovery   在 recovery\<会话>\backup\ 备份原文件，manifest 显式记录 backupPath
3. 剥离 BOM   只删除文件开头的 EF BB BF 三个字节，其余内容一字不改
4. JSON 验证  调用本机 Node 执行 JSON.parse 做等价校验（不是靠正则猜）
5. 重启 DSH   受管启动，重新采集现场
6. 服务验证   健康探针确认服务真的起来了
7. 提交 / 回滚 全部通过 → 提交；任何一步失败 → 自动回滚并如实报告
```

**没有诊断证据不自动改；没有恢复点不写文件；没有验证通过不报「修复成功」；失败必须回滚。**

## 五之二、会话日志定点修复（v1.3.0 新增的第二条可自动修复规则）

`DSH-SESSION-BATCH-031` 只做一件事：**把损坏的会话文件，用你自己归档里的那一份原样覆盖回来。**

```text
1. 体检判定   逐个文件验：zstd 帧结构（含尾部垃圾字节）+ 首帧契约（一行 SessionHeader）
              + seq 连续性；判定「损坏」必须给出具体原因
2. 选归档     只从「校验通过」的归档里取副本；归档校验不过 → 拒绝修复
3. 留档       覆盖前把损坏现场改名 *.corrupt-<时间戳>，绝不删除任何内容
4. 覆盖       把归档里的同路径文件解出来落地
5. 复检       重新体检；复检不通过 → 自动回滚返回现场
6. 报数       如实报告修了几个、留档在哪、复检结果
```

实测口径：修复后的文件 SHA256 与**原始**文件逐字节一致（不是「重建」出来的近似文件）。
管家**永远不会删除**会话：它只会覆盖、留档、回滚。

## 五之三、备份与恢复（v1.3.0 的数据安全链路）

归档固定是四件套：`<名>.tar.gz` + `<名>.sha256` + `<名>.meta.json` + `<名>.redacted.json`。

```text
备份：打包 → 按规则剔除凭据（清单写进 .redacted.json）→ 明文凭据只写本机 vault\ → 写边车文件
校验：逐份核对 SHA256 + 归档可读性；缺 .sha256 一律算「无法确认」，不当通过
恢复：校验通过 → 拍「恢复前快照」→ 现有数据改名挪旁（dsh-home.pre-restore-*，不删除）
      → 落地 → 复算文件指纹 → 按真实剔除清单把凭据从 vault 补回
轮换：用户归档按 backupKeep 保留（默认 7）；升级前 / 恢复前快照单独计数、受保护
```

`--restore ... --dry-run` 全程零改动，只列「哪些条目、覆盖到哪里、当前文件指纹」。

## 六、明确「不自动做」的事

```text
普通 JSON 损坏（无法推断正确内容）
核心依赖版本漂移（无法判断哪个版本才对）
插件与主程序不匹配（可能是有意为之）
未知模块缺失 / 未知插件兼容问题 / symlink 问题
无法确认归属的文件
任何形式的「升级 / 安装 / 构建仓库」
自动删除旧数据（恢复前一律改名挪旁，不删除）
自动装依赖 / 改 profile（只在体检里报「缺什么」，装不装你决定）
自动换 Node 版本、自动改插件版本（兼容性只负责「拦」，不负责「替你做主」）
把凭据明文写进归档（默认脱敏；关闭脱敏要自己改配置）
```

原则：**宁可少修，也不误修。**

所以【一键修复】在只发现「不可自动修复」的故障时，会直接告诉你「未执行任何写入」，并给出人工建议。
体检里的部分红项（例如上游版本策略导致的子包漂移）属于**静态警告**，不影响运行，
详见 [`troubleshooting.md`](./troubleshooting.md) 的说明。

## 七、隐私

诊断数据全部留在本机 `diagnostics-data\`；备份归档默认只落本机磁盘（桌面下的 `dsh-backups`，
可用 `backupDir` 改），归档内**默认不含凭据**（按规则剔除，清单写进 `.redacted.json`），
明文只写本机 `vault\`。程序不上传任何内容。联网只发生在两个明确场景：查询 npm 镜像源与检查本仓库的更新清单。
分享诊断结果或归档前，请自行确认其中不含不想公开的路径信息。
